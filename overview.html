1. Repo Summary

Claw Code is a clean-room Rust & Python re-implementation of an AI coding-agent harness (inspired by Claude Code's architecture). It provides a CLI tool called claw that lets users interact with Anthropic's Claude models through a REPL or one-shot prompts, with a rich tool system that can execute bash commands, read/write files, search code, manage tasks, connect to MCP servers, and more.

The repository has two parallel surfaces:

  • Rust workspace (rust/) — the primary runtime: a 9-crate Cargo workspace producing the claw binary. ~48K lines of Rust.
  • Python workspace (src/) — a parity/introspection layer that mirrors command/tool inventories and provides analysis, reporting, and audit CLIs.

2. How This Differs from the Original Claude Code

This repository is a clean-room rewrite, not a fork. The original Claude Code is a proprietary TypeScript/Node.js agent shipped by Anthropic. This project re-implements the same architectural patterns in Rust and Python without copying source code.

Several subsystems (MCP end-to-end, bash deep validation, session compaction matching) are still in progress.

8. Python Parity Surface

Purpose

The Python src/ workspace mirrors the original agent harness's command and tool inventories. It provides reporting, auditing, and simulation — not a runnable agent runtime.

Key modules

  • main.py — CLI entry with 20+ subcommands
  • query_engine.py — turn simulation, session persistence, compaction
  • runtime.py — PortRuntime routing + bootstrap sessions
  • commands.py / tools.py — 150+ command / 100+ tool mirrors
  • parity_audit.py — archive-vs-workspace diff

9. Tool Surface (40 Specs)

The Rust tools crate exposes 40 tool definitions via mvp_tool_specs(). The execute_tool() function dispatches calls to runtime modules. Tools are organized into groups:

Core File/Code Tools
  • bash
  • read_file, write_file, edit_file
  • glob_search, grep_search
External / Network
  • WebFetch, WebSearch
  • MCP (ListResources, ReadResource, Auth)
  • LSP (symbols, refs, diagnostics, hover)
State / Orchestration
  • Task (Create/Get/List/Stop/Update/Output)
  • Team (Create/Delete), Cron (Create/Delete/List)
  • Agent, TodoWrite, Skill
  • Config, Sleep, REPL, PowerShell
Permission gating: Every tool spec carries a required_permission field. The PermissionEnforcer checks this before execution. File writes are workspace-boundary-gated. Bash is read-only-checked and prompt-escalated.

10. Permission System

Permission Modes
read-onlyNo file writes, no mutating bash commands
workspace-writeWrites allowed inside workspace boundary only
danger-full-accessAll operations permitted (default)
promptInteractive prompt before dangerous operations
Enforcement Layers
  • PermissionPolicy (permissions.rs) — base decision engine with override support and rule configs
  • PermissionEnforcer (permission_enforcer.rs) — tool-level gating, file-write boundary checks, bash read-only heuristics
  • Sandbox (sandbox.rs) — Linux namespace isolation (unshare), container environment detection

Key design decisions

  • No unsafe code — enforced workspace-wide via [workspace.lints.rust] unsafe_code = "forbid"
  • Synchronous tool execution — tools use reqwest::blocking and std::process::Command
  • Global registries via OnceLock — Task, Team, Cron, MCP, LSP registries are session-scoped singletons
  • Config merge order — User → Project → Local (last wins)
  • Trait-based runtime — ConversationRuntime<C: ApiClient, T: ToolExecutor> enables mock injection for tests
